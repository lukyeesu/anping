## 1.6.29: แก้ไขอาการ Crash Loop และ ANR ปิดหรือรอ ขณะเปิดแอป
- **แก้ไข Foreground Service ตามข้อกำหนด Android 14+**: เพิ่มสิทธิ์ `CHANGE_NETWORK_STATE` และ `CHANGE_WIFI_STATE` ใน `AndroidManifest.xml` เพื่อปฏิบัติตามข้อกำหนดความปลอดภัยของ `FOREGROUND_SERVICE_TYPE_CONNECTED_DEVICE` เมื่อเริ่มทำงานโดยยังไม่ได้เสียบเครื่องอ่านบัตร ป้องกัน `SecurityException` และ `ForegroundServiceDidNotStartInTimeException` ที่เป็นต้นเหตุของ ANR ปิดหรือรอ
- **กำจัด Recreation Loop ใน WebView Render Process**: ยกเลิกการเรียก `recreate()` ที่เป็นลูปทำลายและสร้าง Activity ซ้ำๆ ทันทีที่เปิดแอป เปลี่ยนเป็นระบบกู้คืนหน่วยความจำ `handleRenderProcessGone` พร้อมสลับสร้างอินสแตนซ์ WebView ใหม่แบบไดนามิก ป้องกันการค้างและปัญหา UI Thread ถูกบล็อก
- **ย้ายการตรวจสอบ USB สู่ Background Thread**: ดึงการประมวลผล USB Manager (`checkConnectedDevices`, `handleUsbDeviceIntent`) ออกจาก Main UI Thread สู่ Coroutine `Dispatchers.IO` เริ่มต้นแอปเร็วทันที 0ms UI Block
- **เปิดใช้ aaptOptions noCompress สำหรับ Asset หน้าเว็บ**: ไฟล์ Web Bundle ขนาดใหญ่จะถูก map ผ่านหน่วยความจำตรงจาก APK ไม่ต้อง Decompress ผ่าน RAM ของ AssetManager ลดภาระหน่วยความจำและตัดปัญหา OutOfMemory บนแท็บเล็ตทุกรุ่น
- **ความปลอดภัยของ BundledWebContent**: จัดการ Exception ในการอ่าน Asset และเพิ่ม CORS Header ทุกคำขอที่ Intercept แบบครบถ้วน 100%

## 1.6.23: Back กล้อง มือถือจอเล็ก และเลือกหน้าทันทีหลังลาก sidebar

- กล้องเข้าระบบ history ของ `useModal` เช่นเดียวกับฟอร์มที่อยู่ด้านหลัง Back จึงปิดเฉพาะกล้อง และการปิดด้วยปุ่มซ้ายบนไม่ทิ้ง history เกิน ผล OCR ที่ตอบหลังปิดกล้องถูกละทิ้ง
- เครื่องจริงพบ `WebView.canGoBack()` คืน false แม้มี modal อยู่ใน JavaScript history จึงให้ Android ส่ง Back ผ่าน history ของ modal ก่อน แล้วจึงใช้การย้อนกลับ/ออกแอปเดิม
- ตรวจ layout โทรศัพท์ 320×568, 390×844 และแนวนอน 568×320, 844×390 รวมแท็บเล็ตทั้งสองแนว เลื่อนกรอบและข้อความให้พ้นปุ่ม ย้ายไฟแฟลชขึ้นหัวสีขาวเพื่อไม่บังกรอบบนจอเล็ก
- ปลดตัวกันคลิกหลังลากเมื่อมี pointerdown ใหม่ทันที และใช้ touchend ของการแตะนิ่งเลือกหน้า เพราะ WebView อาจไม่สร้าง synthetic click ระหว่าง sidebar เคลื่อน คงการป้องกันการเลือกหน้าจาก gesture ลาก
- Fixture ผ่าน Back/ปุ่มซ้ายบนซ้ำ 3 รอบ, Back ระหว่าง OCR, ไม่ทิ้ง history, layout ทั้ง 6 ขนาด, แตะเลือกหน้าทันทีหลังลากทั้งเมาส์/นิ้ว และการลากช้า/ค้าง/สะบัดเดิม
- แท็บเล็ตจริงผ่านปุ่ม Back ของ Android ปิดกล้องกลับฟอร์ม คืน tracks และ Back อีกครั้งปิดฟอร์มได้; ผ่านการเลือกหน้าทันที 4 กรณีเมาส์/นิ้ว × manual/automatic ไม่บันทึกข้อมูลคนไข้ในการทดสอบ

## 1.6.22: หน้ากล้องสแกนบัตรตามภาพตัวอย่าง

## 1.6.21: โหลดรายชื่อหน้าถัดไปและคืนตำแหน่งเมื่อสลับหน้า

- สังเกตจุดท้ายรายการใหม่เมื่อโหลดเสร็จ แม้หน้าที่ได้รับมีแต่รายการซ้ำ; กรณีโหลดล้มเหลวหรือได้เพียงแคชออฟไลน์ เก็บรายชื่อเดิมและให้กดลองอีกครั้งด้วย cursor เดิม
- เก็บหน้าที่โหลด คำค้น การเรียง และขนาดแถวในหน่วยความจำระหว่างสลับหน้า คืนคนไข้แถวเดิมก่อนวาดและหยุดปรับตำแหน่งทันทีเมื่อผู้ใช้เริ่มเลื่อนเอง
- นัดหมายจำคำค้น รูปแบบรายการ จำนวนแถว และมุมมองปฏิทิน; เปลี่ยนเงื่อนไขค้นหา/เรียง/กรองให้กลับบนสุด ไม่เก็บแบบฟอร์มที่ยังไม่บันทึก

- แท็บเล็ตจริงโหลดหน้าถัดไปและสลับนัดหมายกลับเวชระเบียนผ่าน: คนไข้เดิม คลาดเคลื่อนตำแหน่ง 0px และไม่ไหลต่อในช่วงวัด 500ms; sticky regression ผ่าน 8 gestures / 829 samples ไม่มี missed dock

## 1.6.19: คืน refresh และให้ sidebar/เนื้อหาใช้เวลาเดียวกัน

- ยกเลิกข้อจำกัดเริ่มดึงรีเฟรชเฉพาะ 96dp ด้านบนจาก 1.6.18 คืนการดึงจากเนื้อหาเมื่อหน้าอยู่บนสุด แต่ล็อกท่าปัดขึ้น/แนวนอนไม่ให้กลายเป็น refresh
- ตรวจสถานะเลื่อนจากจุดที่แตะกับหน้าหลัก โดยไม่ใช้สถานะเลื่อนของ panel อื่นมาบล็อก refresh ส่งสถานะใหม่ทุก touchstart และให้ React เป็นเจ้าของการซิงค์แทนการส่งข้อมูลซ้ำจาก native fallback
- กัน refresh บน modal รวมถึงหน้าต่าง `.fixed.inset-0` ที่ไม่ได้กำหนด role
- แก้ timer สั่งจบ sidebar ก่อน width transition จบจริง โดยรอ animation ของ sidebar และเนื้อหาให้เสร็จ
- ระหว่างการสะบัด ให้ก้อนเนื้อหาใช้ keyframes และ startTime เดียวกับ width transition ของ sidebar ผ่าน Web Animations API แทนการเขียน transform ไล่ตาม ResizeObserver ทุกเฟรม คงการลากช้าตามนิ้วและ uniform scale ทั้งสองแกน
- เติมพื้นหลัง filter เต็มขอบตลอดช่วง dock แม้กล่องด้านในยังขยายไม่สุด คง linear motion และมุมมนด้านล่าง 24px
- แก้เพิ่มตามผลใช้งาน: เมื่อ dock ให้กล่อง filter ด้านในโปร่งใส ไม่มีกรอบหรือเงาซ้ำ จึงเหลือพื้นหลังทึบเพียงชั้นเดียว และย้ายทั้งพื้นหลังกับช่องค้นหาตาม clock ของ header
- Header กับ filter ใช้สถานะจาก scrollTop รอบเดียวและ threshold ที่วัดไว้ตอน layout เปลี่ยน ไม่รอ IntersectionObserver แยกกัน จึงไม่ตกหล่นเมื่อปัดข้ามตำแหน่งเร็ว ๆ; ไม่มีการอ่าน geometry ทุก scroll event
- Clip เนื้อหา header ตามความสูงพื้นหลังที่กำลังย่อ ป้องกันคำอธิบายล้นลงมาทับ filter ระหว่าง animation

เครื่องจริง: ความคลาดระหว่างความกว้างเนื้อหากับพื้นที่ข้าง sidebar สูงสุดจากประมาณ 29.98px เหลือ 0.43px ในชุดสะบัด 6 ครั้ง จุดจบครบ 80/256px; ทดสอบลาก 48 ท่าครบเวชระเบียน/นัดหมาย/บอร์ดผู้บริหารผ่าน
ดึงจากเนื้อหาบนเครื่องจริงแล้วตรวจพบ document reload หนึ่งครั้ง โดยไม่ได้บังคับค่า scroll ของ native ใน test มีผลวัดและข้อจำกัดใน `DEVICE-PERFORMANCE.md`
ชุด sticky สุดท้ายผ่าน 50 การข้ามตำแหน่งเร็วภายใต้ CPU throttling 4 เท่า และ trusted native scroll 8 ท่า / 379 frames ไม่พบ missed dock; รอยต่อประมาณ -0.996 ถึง -0.991px

## 1.6.17: ปัดเร็วแล้วให้ sidebar เคลื่อนอัตโนมัติ

- การปัดเร็วใช้เป็นคำสั่งเปิด/ปิด เริ่ม linear 260ms ตั้งแต่จับทิศทางได้ ไม่เปลี่ยนความกว้างทีละ touchmove จึงเดินต่อได้แม้พิกัดนิ้วส่งมาเว้นช่วง และไม่เริ่ม animation ใหม่ตอนยกนิ้ว
- ใช้การเคลื่อนแนวนอนเกิน 8px ภายในช่วงเริ่ม 160ms และความเร็วเกิน 0.22px/ms เลือกโหมดอัตโนมัติ การลากช้า/กดค้างก่อนลากยังตามนิ้วโดยตรง และยังกลับทิศเพื่อเปลี่ยนคำสั่งก่อนปล่อยได้
- จับเวลาจาก event.timeStamp เพื่อแยกการปัดเร็วจริงออกจากความล่าช้าในการส่ง event ให้ JavaScript ป้องกันกรณีปัด 15ms แต่ส่งถึงโค้ดห่างกัน 120ms แล้วถูกเข้าใจผิดว่าเป็นการลากช้า
- รอให้ทั้ง gesture และ animation จบก่อนคืน native pull-to-refresh รวมถึงกรณี animation จบแล้วแต่ยังแตะค้างอยู่
- ทั้งก้อนเนื้อหาและ sidebar ยังย่อ–ขยายพร้อมกันตามรูปแบบเดิม ไม่เปลี่ยน UI ของ header/filter หรือ Finance

ผ่าน PC ทั้ง touch/mouse, สองทิศ, เว้นส่งพิกัดแล้วภาพยังเคลื่อน, ปล่อยแล้วไม่ restart, แตะค้างจน animation จบ และกรณีส่ง event ล่าช้า
บนแท็บเล็ตจริงผ่าน 48 gestures ครบ 3 หน้า: flick ใช้โหมด automatic โดยไม่เข้าสู่ manual scrubbing; hold/slow ยังเข้าสู่ manual และทุกครั้งจบ 80/256px ถูกด้านโดยไม่ค้าง flags
นี่คือการเปลี่ยนวิธีรับท่าปัดเพื่อลดจังหวะเหมือนการแตะขาดช่วง ไม่ใช่การรับรองว่าไม่มีเฟรมช้าในทุกภาระงาน

## 1.6.16: สถานะ sticky ค้าง, linear sidebar และ Finance (ประวัติรุ่นก่อน)

- Header โปร่งใสเฉพาะเมื่ออยู่บนสุด เริ่มเลื่อนแล้วพื้นหลังขาวทึบ และคงทึบระหว่างคืนขนาดจนกลับถึงบนสุด แยกสถานะพื้นหลังออกจากสถานะย่อ/ขยาย ไม่ fade ให้แถวข้อมูลลอดผ่านขณะเลื่อนช้า

- การตัดสินสะบัดใช้การเคลื่อนไหวช่วงท้าย 100ms แยกช่วงกดค้างและการกลับทิศ รวมพิกัด mouseup ที่อาจไม่ทันเข้า mousemove/rAF และใช้ความกว้างจริงตอนเริ่มจับ รองรับมีเพียง down/up โดยไม่มี move และกัน jitter กลับทางที่ยังไม่ถึง 8px

## 1.6.15: สะบัดสั้นทั้งสองทิศและ modal เวชระเบียน (ประวัติรุ่นก่อน)

filter ย้าย/ขยายเป็นชั้นภาพ และเลิกสลับ absolute/relative ตอนชน header; ล้าง translate เดิมเพื่อไม่ให้ตำแหน่งซ้อนกัน
หยุด listener เดิมเฉพาะการตกแต่ง sticky ส่วน pagination และการโหลดข้อมูลทำงานต่อ
เส้นทางนี้ใช้บนจอกว้างตั้งแต่ 768px เมื่อ engine รองรับ ScrollTimeline และ animation-range; จอเล็กหรือ engine ที่ไม่รองรับยังใช้เส้นทางเดิม โดยจำกัด progress ไว้ที่ header แทนทั้ง main
หลักการอ้างอิง: [Chrome: scroll-driven animations](https://developer.chrome.com/docs/css-ui/scroll-driven-animations)

ตรวจ Chromium ทั้งเส้นทางเว็บปกติและ APK ด้วยข้อมูลจำลอง 200/1,000 คนไข้, header flow คงตัว, การย่อที่ระยะกลาง, filter จอดใต้ header, คลิกปุ่มเพิ่ม/ค้นหา และวงจร sidebar/modal/resize ผ่าน
บนแท็บเล็ตเพิ่ม Android input จริงแบบกดค้างก่อนลาก, ลากช้า 1,600ms, ลากเร็ว 180ms และสะบัด 40ms ทั้ง sticky และ sidebar
sidebar ครบ 48 ครั้งบนสามหน้าหลัก ย่อ/ขยายจบถูกต้อง ไม่มีสถานะลากค้าง แต่ยังมีเฟรมเกินกำหนด โดยเฉพาะการสะบัดสั้น ไม่รับรองว่าเฟรมสะดุดหายทั้งหมด

การแก้เว็บอยู่ใน source; เว็บ production ยังไม่เปลี่ยนจนกว่าผู้ใช้จะเผยแพร่เอง ไม่มีการ stage/commit/push หรือ deploy

## รุ่น 1.6.11 ที่ผู้ใช้ไม่รับพฤติกรรม

รอบ 1.6.11 ทดลองแบ่ง sidebar กับเนื้อหาทั้งหน้าเป็นสองก้อน
เฉพาะเวชระเบียน นัดหมาย และบอร์ดผู้บริหารใน APK ระหว่างลากจะตรึงความกว้างของก้อนเนื้อหาและให้ sidebar ดันทั้งก้อน โดยไม่ scale ตัวอักษรหรือกราฟ
เมื่อปล่อยและ sidebar จัดตำแหน่งจบ จึงคืน responsive layout หนึ่งครั้ง พร้อม crossfade ของ viewport เนื้อหา 140 ms เพื่อลดรอยต่อ ไม่ขยาย/ย่อภาพระหว่าง crossfade
ขณะลากก้อนที่คงขนาดเดิมอาจเกินกรอบหรือมีพื้นที่ว่างด้านขวาระหว่างย่อ sidebar; เมื่อปล่อยจะจัดให้พอดีพื้นที่ใหม่
ใช้เลเยอร์ของ DOM และ snapshot ชั่วคราวของ View Transition ในหน่วยความจำ ไม่บันทึกภาพหน้าจอไว้ในแอป
ไม่ใช้กฎ pointer-events ที่สืบทอดไปทุก cell บนสามหน้านี้ แต่ใช้ชั้นรับสัมผัสระหว่างเคลื่อนไหวเพื่อกันกดเนื้อหาโดยไม่ตั้งใจ
ยกเลิกเลเยอร์เมื่อ resize, เปลี่ยนหน้า, รับ smartcard-read หรือเปิดตัวตรวจบัตร และไม่ตรึงก้อนเมื่อมีฟอร์มเวชระเบียนเปิดอยู่
Browser ปกติ หน้าอื่น และ WebView ที่ไม่มี View Transition คงเส้นทางเดิม; ไม่บังคับ 60 Hz หรือเปลี่ยน GPU renderer

แม้ผลตัวเลขดีขึ้น ผู้ใช้เห็นการเคลื่อนและการจัดขนาดทำงานแยกกัน จึงแทนที่ด้วย 1.6.12

รอบ 1.6.10 ทำ `fetchQueueForMonth` และ `fetchPatientTreatments` ให้มี reference คงตัวเมื่อข้อมูลที่เกี่ยวข้องไม่ได้เปลี่ยน
การย่อ/ขยาย sidebar จึงไม่ทำให้ปฏิทิน render ใหม่และไม่ถอด/สร้างตัวฟัง realtime ของเวชระเบียนที่เปิดอยู่ซ้ำ
เฉพาะ HTML ใน APK ใช้ passive touchmove listener โดยยังคง `touch-action: pan-y` บน sidebar และ `none` บนขอบลาก ส่วน browser ปกติคงเส้นทางรับสัมผัสเดิม
ไม่เพิ่ม CSS containment หรือเปลี่ยน ResizeObserver หลังผลทดลองยังไม่แสดงประโยชน์ที่แน่นอน

รอบ 1.6.9 ลดการคำนวณสไตล์ซ้ำโดยอัปเดต opacity/transform เฉพาะข้อความ sidebar และป้องกันการเขียน stylesheet เดิมซ้ำเมื่อ App render
ทำ callback แจ้งเตือนให้คงตัว เพื่อไม่ให้การย่อ/ขยาย sidebar เปลี่ยนตัวเรียก API จนบอร์ดผู้บริหารโหลดข้อมูลและเริ่มแอนิเมชันใหม่
พักแอนิเมชันกราฟวงกลมระหว่างลาก ลดเงา SVG ชั่วคราว และปิด blur ของ sticky header ที่กฎใน 1.6.8 ยังครอบคลุมไม่ถึง
ในรอบ 1.6.9/1.6.10 เนื้อหายังปรับความกว้างตาม sidebar ทุกเฟรม ไม่ใช้ภาพหน้าจอแทนเนื้อหาหรือยืดสัดส่วนข้อความ

รุ่นนี้บรรจุ production build ของเว็บเดิมลง APK เพื่อให้ติดตั้งแล้วได้รับโค้ดทดลองทันที โดยคง origin `https://anpingclinic.vercel.app` และเส้นทาง `/records/...` เดิม
API, authentication, ไฟล์ดาวน์โหลด และ JSON ตรวจอัปเดตยังเรียกเซิร์ฟเวอร์จริง ข้อมูลที่บันทึกผ่านแอปจึงเป็นข้อมูลจริงเช่นเดียวกับ Native demo
การเปลี่ยนหน้าตาเว็บบนเซิร์ฟเวอร์ภายหลังจะไม่แทนที่ snapshot ใน APK นี้ ต้อง build APK ใหม่
ไม่ได้เปลี่ยน `public/clinic-version.json` เพื่อประกาศอัปเดตให้ผู้ใช้ทุกเครื่อง

สิ่งที่ทดลองปรับ:

- คง sidebar แบบดันเนื้อหา ใช้ RAF เดียวต่อเฟรม และเริ่ม gesture เพียงชุดเดียว
- อัปเดต React state หลังแอนิเมชันจบ ลดการชนกับงานลาก
- เก็บ transform ขององค์ประกอบไว้ ลด blur และพักเงา/แอนิเมชันบางส่วนระหว่างลาก
- ให้ ResizeObserver ของรายการเสมือนทำงานผ่าน RAF และพักตัวเลขวิ่งบนบอร์ดระหว่างลาก
- ลดงานตรวจ DOM ใน native scroll bridge และย้ายการรอ USB read lock ตอนถอดเครื่องอ่านไป IO thread
- ทำลาย WebView ที่ renderer หยุดทำงานก่อนสร้าง Activity ใหม่

สร้างจากรากโปรเจกต์ Android:

```powershell
.\gradlew.bat --project-cache-dir .work/gradle :app:assembleRelease --console=plain
```

Gradle เรียก `../scripts/build-webview.mjs` อัตโนมัติ ผลลัพธ์อยู่ที่ `.work/app-build/outputs/apk/release/app-release.apk`
สคริปต์จัดเฉพาะไฟล์เว็บตาม allowlist และทำ manifest พร้อม SHA-256 ไม่บรรจุ APK/ZIP ซ้อนใน APK

การตรวจบนคอมพิวเตอร์ใช้ข้อมูลจำลองชุดเดียวกับ Native demo ที่ 200/1,000 คนไข้ ทดสอบเวชระเบียน นัดหมาย และบอร์ดผู้บริหาร รวมการลากต่อเนื่อง การคืนขนาด sidebar การยกเลิก gesture และกราฟที่ยังแสดงครบ
ผลบนคอมพิวเตอร์ยืนยันการทำงานใน Chromium เท่านั้น รอบ 1.6.11 เพิ่มการวัดบนแท็บเล็ตตาม DEVICE-PERFORMANCE.md แล้ว แต่ยังไม่ได้ทดสอบอ่านบัตรผ่านเครื่องอ่าน USB จริงระหว่างลาก

## ผลเทียบ 1.6.8 → 1.6.9 บนคอมพิวเตอร์

Chromium headless, viewport 1280×800, CPU throttling 4×, คนไข้จำลอง 1,000 ราย/นัดหมาย 200 รายการ/กราฟพร้อมข้อมูล ลากสลับเปิด–ปิด 6 ครั้ง ครั้งละ 20 touchmove แล้วรอให้ sidebar จัดตำแหน่งจบ
วัดทีละรุ่นจาก production assets พร้อม mock เครือข่ายทั้งหมด ไม่มีการเขียนข้อมูลจริง

| เวชระเบียน | 3,914 | 2,141 | 116.7 → 66.6 |

ตัวเลขนี้เป็น stress test ของ Chromium บนคอมพิวเตอร์ ไม่ใช่ FPS หรือ frame time ของแท็บเล็ต และไม่ยืนยันว่าจะลื่นเท่า Native

## ตรวจรอบ 1.6.10

- ใช้ snapshot ของ 1.6.9 เป็นตัวเทียบ ในสองครั้งที่ sidebar ย่อ/ขยาย callback ของปฏิทินเดิมเปลี่ยน 2 ครั้ง รุ่นใหม่ไม่เปลี่ยนและไม่ render ปฏิทินซ้ำ
- ขณะเปิดเวชระเบียน การเปลี่ยนสถานะ sidebar สองครั้งทำให้รุ่นเดิมสร้างตัวฟัง realtime เพิ่ม 2 ครั้ง รุ่นใหม่ไม่สร้างเพิ่ม โดยยังเปิดประวัติและอ่านข้อมูลได้
- ตรวจด้วย trusted touch ทั้งขอบลากและตัว sidebar พร้อมยืนยันว่าแนวตั้งยังเลื่อนเมนูได้ ไม่ย่อ/ขยายหรือเปลี่ยนหน้าเอง
- ตรวจ stylesheet ที่ไม่ถูกเขียนซ้ำ กราฟที่ยังอยู่ครบ การคืนขนาด sidebar, touchcancel, pull-to-refresh และข้อมูลจำลอง 200/1,000 คนไข้ โดย mock ทั้ง HTTP และ WebSocket
- release build ผ่าน ตรวจลายเซ็น/package/versionCode และ SHA-256 ของ assets ใน APK ครบ

รอบนี้เวลาเรนเดอร์บนเครื่องทดสอบแกว่งระหว่างรัน จึงไม่สรุปเปอร์เซ็นต์ FPS/ความเร็วเพิ่มจาก 1.6.9 ผลที่ยืนยันได้คือการตัด render และการสร้าง listener ซ้ำ ส่วนความเนียนต้องเทียบบนแท็บเล็ตจริง
บันทึกเวลาใน `.work/perf-baseline169.json` และ `.work/perf-after1610.json` เป็นผล stress test CPU 4× รอบละ 4 gesture ไม่ใช้เทียบตรงกับตาราง 1.6.8 → 1.6.9 ที่รัน 6 gesture
